## 🚀 v2.0 核心重构与 BUG 修复说明

### 1. 已修复的 13 项关键缺陷（v1.0.0 审计）
1. **修复全站双重 `layout()` 嵌套渲染 BUG**：v1.0.0 中 `src/views/*.ts` 内部已调用 `layout()`，而 `src/routes/*.ts` 又外包了一层 `layout()`，导致全站所有页面出现双层 `<html><body>`、双侧边栏、双顶栏，且 `app.js` 被加载执行两次（点击一次「添加商品」新增两行、二次确认弹窗触发两次）。v2.0 已彻底解耦视图组件与外层布局。
2. **修复初始化/注册/改密永远报「两次密码不一致」的阻断级 BUG**：表单输入框名为 `confirm_password`，而后端读取 `fields.confirm`，导致无法完成初始化、无法注册、无法改密。现已全面对齐并兼容。
3. **补全商品分类「重命名与排序」路由（`POST /categories/:id/rename`）**：修复原版点击分类重命名直接报 404 的问题，并支持分类排序权重调整与关联商品数展示。
4. **修复筛选与分页参数名不一致导致筛选失效的 BUG**：统一商品分类（`category_id` / `categoryId`）、库存流水（`product_id` / `productId`）、分佣管理（`sales_id` / `salesId`）参数解析。
5. **修复同单多行重复商品绕过库存校验及流水断链 BUG**：在采购、销售、退货及作废回滚中按商品实时递推运行态库存，杜绝拆行超卖及 `before_qty` → `after_qty` 断链，并采用**加权平均法**动态更新商品进货成本。
6. **补全商品建档「期初库存」流水（`initial_in`）**：新建商品录入期初库存 > 0 时自动写入期初入库流水，确保库存台账从 0 到当前值 100% 闭环可追溯。
7. **落地客户「赊账授信额度（`credit_limit`）」硬性风控与欠款补收核销**：开单时自动核算客户当前累计欠款 + 本单欠款是否超授信额度；在销售单详情页新增「欠款补收核销（`POST /sales/:id/pay`）」。
8. **新增销售退货单原单校验与作废回滚（`POST /returns/:id/void`）**：关联原销售单退货时自动校验原单商品与可退数量，支持退货单作废回滚，并修复经营报表中退货汇总未过滤 `status='done'` 及毛利未扣除整单优惠的偏差。
9. **修复用户管理与销售团队字段丢失及层级越权**：修复新增销售员丢失手机号、编辑用户无法修改角色与状态、二级销售仍能看到「新增销售员」按钮、以及将有下属的一级主管直接降级导致树断裂的问题。
10. **修复个人中心会话注销水平越权漏洞（IDOR）与缺失的 CSRF 校验**：`POST /profile/sessions/:id/revoke` 严格限定 `user_id` 归属，并为批量结算、立即备份、踢出其他设备补全 CSRF 令牌校验与操作按钮。
11. **修复东八区（UTC+8）跨日统计错位**：14 天销售趋势图改用 `datetime(created_at, '+8 hours')` 聚合，修复北京时间 00:00~08:00 订单被算入前一天的 BUG。

### 2. 企业级 UI 全面重构亮点
- **现代 SaaS 视觉体系**：采用高对比度 Slate & Royal Blue 企业级配色，内置 **深浅色主题切换（🌓 Dark Mode）**。
- **双栏品牌认证中心**：登录、初始化、客户注册与密保找回采用双栏沉浸式卡片布局。
- **分组侧边导航 + 顶栏快捷操作区**：支持实时低库存角标提醒、一键开单/入库快捷入口与个人中心直达。
- **POS 级智能开单与商业凭证打印**：实时联动计算「商品小计 - 优惠折扣 = 折后应收 / 挂账欠款」，支持一键填入全额实收；单据详情页内置 `@media print` 商业凭证打印样式，一键打印 A4 出入库单。

## 💳 v2.3 客户余额账户与余额支付

### 1. 数据模型
- `users.balance`：客户可用余额（元），默认 0，**不允许透支**。
- `balance_logs`：余额流水表，每笔变动记录 `变动金额 / 变动前 / 变动后 / 类型 / 关联单据 / 经办人 / 备注`，类型含 `recharge 充值`、`consume 消费`、`void 作废退回`、`adjust 手工调整`、`refund 退款`。
- 迁移文件 `migrations/0002_balance.sql`；`ensureSchema()` 同步改为**每次启动都跑一遍幂等升级**（`ALTER TABLE ... ADD COLUMN` + `CREATE TABLE IF NOT EXISTS`），空库自建、存量库补字段、未执行迁移的环境都能自动补齐。

### 2. 客户余额充值 / 扣减
- 客户详情页（`/customers/:id`）新增 **💳 客户余额账户** 卡片：顶部展示可用余额，中间是「充值 / 扣减」表单，下方是最近 20 笔余额流水（含关联销售单跳转）。
- 正数为充值、负数为扣减；**销售员只能充值，扣减仅管理员可执行**；扣减后余额不得小于 0。
- 客户列表（`/customers`）新增「账户余额」列，并提供「💰 充值」快捷入口。

### 3. 余额支付（结算方式新增 `balance`）
- 销售开单 / 客户自助下单 / 欠款补收的下拉框均新增「余额支付」，与微信、支付宝、现金、银行转账并列。
- 选择「余额支付」时：**按应收全额扣减客户余额**，实收金额自动填满并锁定（不允许「部分余额 + 部分挂账」，避免账目混乱）；散客（无 `customer_id`）不能使用余额支付。
- 服务端三重校验：客户必须存在且为 `customer`、余额必须 ≥ 应收、扣款与订单/库存/佣金**同一 `db.batch()` 提交**，保证「扣款成功 ⇔ 订单成立」。
- 前端实时联动：选中客户后「余额支付」选项文案变为「客户可用 ¥X」，切换结算方式时提示条显示「客户当前可用余额 ¥X，本单将扣减 ¥Y，扣后余额 ¥Z」，余额不足时红字提示差额。
- 欠款补收（`/sales/:id` 的「💳 欠款补收核销」）也可选余额支付，按补收金额扣减。

### 4. 作废自动原路退回
- 作废销售单时，按 `balance_logs` 中该单的**净扣款额**原路退回客户余额，并写入一条 `void` 类型流水；重复作废因净额为 0 不会重复退款。
- 退款金额与库存回滚、佣金撤销同批提交。

### 5. 客户侧展示
- 个人中心新增「💳 我的账户余额」卡片：大字号余额 + 最近 10 笔流水，下单时可直接选择余额支付。
- 顶栏与侧边栏仍走 `SafeUser`，已同步暴露 `balance` 字段供后续扩展。

### 6. 边界说明
- 余额扣减采用**条件 UPDATE**（`WHERE ROUND(balance + ?,2) >= 0`）原子执行，避免并发下「先读后写」把余额写成负数。
- 销售退货单若关联的原销售单是「余额支付」，退货金额会**自动原路退回客户余额**（见 v2.4）；其他结算方式仍只回补库存，货款需线下处理或手工充值备注。

## 🔍 v2.4 客户退换货申请与管理员审核

### 1. 数据模型
- 新增 `return_requests` 表（`migrations/0003_return_requests.sql`）：`request_no` 申请单号（`RQ...`）、`customer_id / sales_order_id / sales_order_no`、`type`（`return 退货` / `exchange 换货`）、`reason` 申请原因、`items_json` 商品快照（含成交价、名称、SKU、单位）、`total` 申请金额、`status`（`pending / approved / rejected / cancelled`）、`return_order_id` 关联正式退货单、`review_remark / reviewer_id / reviewed_at` 审核信息。
- `ensureSchema()` 的幂等升级列表同步加入该表与 3 个索引，存量库启动即自动补建。

### 2. 客户侧：申请 → 查看 → 撤销
- 销售单详情（`/sales/:id`）对客户展示 **↩️ 申请退换货**，进入 `/returns/apply?order_id=...`；已作废订单直接拦截并提示。
- 申请页用**单选卡片**选择「🔄 退货退款 / 🔁 换货」，逐行填写申请数量；「可申请数量」= 原单售出 − 历史已退 − 待审核占用，并显示「已退 X · 待审 Y」，超出时红字提示。
- 客户菜单新增 **退换货申请**（`/returns/my`），支持按状态筛选、查看详情、**撤销**待审核申请（`POST /returns/my/:id/cancel`）。

### 3. 管理侧：审核通过 / 驳回
- 管理员与销售菜单新增 **退换货审核**（`/returns/requests`），顶部显示「共 N 条申请 · M 条待审核」，可按状态筛选；**仅管理员可执行审核**，销售员只读。
- 审核详情页展示申请类型、原单、申请人、金额、原因、商品明细；管理员可填审核意见后 **✅ 审核通过并生成退货单** 或 **✖ 驳回申请**。
- 通过时自动调用 `createReturnOrder()` 生成正式退货单（`RT...`）并回补库存，申请单与退货单双向关联；驳回原因客户在详情页可见。
- 审核前二次校验可退数量，历史退货/待审占用已扣除，杜绝「同一件商品退两次」。

### 4. 退货退款与余额联动
- 原销售单为**余额支付**时，审核通过生成退货单会按退货金额**原路退回客户余额**（`refund` 流水，与库存回补同一 `db.batch()`）；现金/微信/银行等结算方式只回补库存。
- 作废退货单会**扣回已退余额**（`void` 流水），余额不足时拒绝作废并提示；作废整张销售单时，退款额会先扣掉退货单已退部分，避免重复退款。

### 5. 自助下单（`/shop`）体验调整
- **默认结算方式为「余额支付」**，选项文案直接显示「可用 ¥X」；若余额为 0 则回退到首个可用渠道，避免默认选中一个必然失败的选项。
- **微信 / 支付宝 / 银行转账只有商家在系统设置里配置过才出现**（`wechat_qr_key` / `alipay_qr_key` / 银行户名、开户行、账号），未配置则下拉框里根本没有该选项；服务端 `POST /shop` 同样按已配置渠道白名单校验，伪造提交会提示「请选择有效的结算方式」。
- **商品明细可以删到零行**：删空后展示「🛒 商品明细已清空，点击下方「＋ 继续添加商品」重新选购」占位，合计归零并禁用提交按钮，同时清空购物车 cookie；重新从商品目录加购后恢复正常。

### 6. 窄屏适配
- ≤860px：顶栏隐藏品牌面包屑与用户名/角色徽章，页面标题单行显示；退换货申请表格隐藏「成交单价 / 已购数量」两列（`.col-hide-sm`），保证「本次申请数量」输入框始终可见。

##  v2.5 退货闭环修复（可退数量与订单联动）

### 1. 修复「一张销售单可以无限办理退货」
- **根因**：`POST /returns/new` 只在「关联原销售单号」文本框非空时才走可退数量校验，从订单页点「办理退货」进入后把单号清空（或写错）即退化为**无原单退货**，数量、商品、次数全部不受约束，可反复回补库存并虚增退款。
- **原单锁定**：从订单页进入时，单号输入框改为 `readonly` 并附带隐藏 `sales_order_id`；服务端以该 id 为准强制关联，单号与 id 不一致直接拒绝并提示「请回到订单页重新点击办理退货」，清空文本框不再能绕过校验。
- **单号精确查单**：新增 `getSalesOrderByNo()`，按 `order_no` 唯一索引精确命中，替换原先「LIKE 模糊搜索 + 前 10 条里挑相等的那条」。
- **退货单价封顶**：关联原单时退货单价不得高于原成交单价（`退货单价 X 高于原成交单价 Y`），杜绝借退货抬高退款额。
- **退货客户一致性**：关联原单时退货客户必须与原单客户一致，避免退款串到别的客户余额。
- 无原单的零售退货仍然允许，但只能从「＋ 新建退货单」主动进入，且提示文案已写明该语义。

### 2. 「办理退货」预填改为**可退数量**
- 旧版每次都按原单**售出数量**预填，等于反复诱导提交同一批货；现按 `可退 = 售出 - 有效退货单已退` 预填，全部退完时不再预填任何行。
- 同一商品在原单里有多行时按商品**合并为一行**（旧版会带出多行、相加后必然超量报错）。
- 明细提示区逐款列出「售出 / 已退 / 本次可退」，报错文案同样带上这三个数字，无需回查订单。

### 3. 销售订单页同步展示退货结果
- 明细表新增「已退数量」列（商品级汇总，重复行只在首行显示，其余标注「同上行」），管理员、销售员、客户三种角色均可见。
- 新增「↩️ 本单退货记录」卡片：列出本单全部退货单（含已作废）的单号、退款金额、经办人、状态、时间与原因，底部汇总「本单应收 · 已退 · 实际成交」；凭证区同步补「本单已退」字段。
- **商品全部退完后，「办理退货 / 申请退换货」按钮不再出现**，改为「该单商品已全部退回」提示；销售订单列表状态列追加「已退 N 单」红色标记（`listSalesOrders` 附带 `return_cnt`）。

### 4. 采购进货单去掉手工加行按钮
> ⚠️ 本节口径已被 [v2.10](#-v210-单据商品明细默认不再预渲染空白行) 取代：初始空行取消后，采购单恢复了「＋ 添加商品行」按钮，否则从进货列表直接新建将没有任何录入口。

- 新建采购进货单（`/purchase/new`）**移除「＋ 添加商品行」与「＋ 继续添加商品」两个按钮**，与退货单口径一致：明细只保留服务端渲染的初始空行（从商品档案点「📥 进货」进入时预选该商品）。
- 实现复用 `orderItemsBlock()` 的 `allowAddRow: false` 分支，无新增渲染路径；一张进货单对应一个商品，多商品采购需分单创建，便于按单核对供应商实付与加权成本。
- 初始空行仍可改商品、数量、单价；删除按钮在只剩一行时提示「一张单据至少需要保留一行商品明细」，提交链路 `parseItems()` 与服务端校验未改动。

##  🗂️ v2.8 商品二级分类 + 管理端导航收敛

### 1. 分类树：一级 / 二级两层，两级都能挂商品
- `categories` 新增 `parent_id`（`NULL` = 一级分类），分类页改为两级树：一级行 `cat-root`、二级行 `cat-sub` 带「└」缩进，标题显示「分类结构（X 个一级 · Y 个二级）」。
- **一级和二级都可直接挂商品**，`products.category_id` 语义不变，历史数据零迁移；商品列表、编辑页、画册、CSV 导出的分类名统一渲染为层级路径 `数码配件 / 充电宝配件`（`CATEGORY_NAME` / `CATEGORY_JOIN` 两处 SQL 片段收敛，不再各写一遍 JOIN）。
- 建档与筛选的分类下拉改用 `categoryOptions()`：有子级的一级渲染成 `<optgroup>`，一级自身保留为「数码配件（直属）」选项，二级前加全角空格缩进；无子级的一级仍是普通选项，避免出现只有一个成员的空分组。
- 商品列表按一级筛选时**级联包含其下全部二级**（`Store.categoryScope()` 展开成 `IN (...)`）；按二级筛选则只出该二级。经营看板的「分类库存价值占比」按**一级汇总**（`COALESCE(pc.id, c.id)`），二级不单独占一条，占比图不会被打碎。

### 2. 重名规则与迁移（`migrations/0004_category_tree.sql`）
- 旧表把 `name` 写成了建表级 `UNIQUE`（全站唯一），二级分类无法在不同一级下重名。SQLite 不能 `ALTER` 掉建表约束，只能**整表重建**：新表 `id` 原样拷贝（`products.category_id` 无外键约束，引用不断），唯一性改为表达式索引 `CREATE UNIQUE INDEX uq_categories_parent_name ON categories(IFNULL(parent_id,0), name)`——**同一父级下唯一，不同一级下允许同名**（`IFNULL` 让 NULL 父级也参与去重）。
- 本地开发无需手动跑迁移：`ensureSchema()` 里的 `upgradeCategoryTree()` 会读 `sqlite_master` 的建表 DDL，检测到旧约束就自动执行同一套重建步骤；步骤写成 `CREATE IF NOT EXISTS → INSERT OR IGNORE → DROP → RENAME → 建索引`，并额外补一条「`categories__v2` 残留且 `categories` 缺失 → 直接补完 RENAME」的恢复分支，中途崩溃可重入。
- 备份兼容：`exportBackup()` 用 `SELECT *`，新列 `parent_id` 自动带出；`importBackup()` 按每行自身的键拼 `INSERT`，因此**导入 v2.8 之前的旧备份不会报错**，缺 `parent_id` 的分类一律落为一级分类。

### 3. 层级约束与删除保护（服务端裁决，不靠前端）
- `resolveParent()` 统一校验：上级必须存在、必须是**一级**（选到二级报「『X』本身是二级分类，分类最多只支持两级」）、不能挂到自己下面；`POST /categories` 与 `POST /categories/:id/rename` 共用。
- **有子分类的一级不允许降级为二级**（提示「请先处理子分类再把它降为二级」），前端直接把该行的上级下拉 `disabled` 并给出 `title` 说明；二级改选「＋ 作为一级分类」即升级为一级。
- **有子分类的分类禁止删除**（提示「『X』下还有 N 个二级分类，请先删除子分类或把它们改挂到其他一级分类」），删除叶子分类时其下商品自动归为「未分类」，审计日志记录「删除分类 名称（#id），N 款商品已归为未分类」。
- 分类计数区分口径：一级显示「直属 N 款」+「含 K 个二级共 M 款」，二级只显示「N 款商品」。

### 4. 管理端侧栏收敛：删掉「采购进货 / 销售开单」
- 商品档案页每行本来就有「📥 进货」「🧾 开单」直达按钮，顶栏快捷区也常驻「＋ 销售开单」「📥 采购入库」，侧栏再放两个列表入口属于重复。`ADMIN_MENU` 的「进销业务」分组现只剩**销售退货 / 退换货审核**两项。
- 为免入口丢失，商品档案页头补上「📥 进货单记录」`/purchase` 与「📤 销售单记录」`/sales`（分别按 `canPurchase` / `canSell` 显示），`/purchase`、`/sales` 路由与权限完全不变，仅去掉导航位；销售员角色的 `SALES_MENU` 未受影响。

## 💳 v2.9 收款方式收敛：下线「现金」与「挂账/赊销」

### 1. 三处下拉同时去掉 `cash` 与 `credit`
- **客户自助下单**「意向结算方式」：`customerPayMethods()` 不再追加 `cash` / `credit`，只剩「余额支付」+ 商家在系统设置里实际配置过的微信 / 支付宝 / 银行转账。
- **商家代客开单**「收款方式」：固定列表由 `wechat, alipay, cash, bank, balance, credit` 收敛为 `wechat, alipay, bank, balance`。
- **销售单详情 · 欠款补收核销**：由 `wechat, alipay, cash, bank` 收敛为 `wechat, alipay, bank`（关联了客户的单据仍额外给出「余额支付」）。
- 服务端 `POST /shop` 的白名单本就取 `customerPayMethods()`，因此客户伪造 `payment=cash` / `credit` 会被直接拒为「请选择有效的结算方式」，无需另加校验。

### 2. 挂账能力没有消失，只是不再是一个「选项」
- 欠款仍由**实收 < 应收**自然产生：代客开单填 220 应收 / 100 实收，单据照样记 120 元待收挂账欠款，并按客户 `credit_limit` 校验授信上限。
- 客户档案「当前挂账欠款」、看板「客户应收欠款」、欠款补收核销、`/users/:id` 的授信额度录入**全部保留**，用于处理历史与新产生的欠款。

### 3. 历史数据只读展示，不做清洗
- `PAYMENT_NAME` 保留 `cash: 现金` / `credit: 挂账/赊销` 两条映射，历史销售单列表、详情、CSV 报表照旧显示原收款方式；`paySalesOrderDebt()` 在挂账单结清后会把展示值改写成实际补收渠道。
- 未做数据迁移：把历史单据批量改写成其他渠道会让账目与原始凭证对不上。

### 4. 兜底提示：客户无可用渠道时不再静默失败
- 若商家尚未配置任何收款渠道且客户余额为 0，「意向结算方式」下方直接给出说明：「商家暂未开放微信 / 支付宝 / 银行转账收款，您的账户余额也不足，本单无法提交，请联系客服充值或确认收款方式。」——避免客户提交后才收到「余额不足」。

- 带上下文的入口不变：从商品档案点「📥 进货 / 🧾 开单」（`?product_id=N`）仍会渲染**该商品的一行预填明细**（含标准价与行小计），只有真正无预选时才留空。
- 客户自助下单页沿用购物车：有商品即逐行渲染（单价锁定为系统售价），购物车为空时提示「🛒 购物车是空的，点击下方「＋ 继续添加商品」前往商品目录选购」，该页仍不提供手工增行。

### 2. 实现：`<template>` 下发空白行结构
- `orderItemsBlock()` 去掉 `allowEmptyRows` 选项与 `data-allow-empty` 标记，新增 `emptyHint`；明细区为空时把一份行结构包进 `<template id="itemRowTemplate">`（`<template>` 内容不随表单提交，也不会参与校验）。
- 已有预填行的页面不再重复下发整张商品下拉：`app.js` 首次点击「＋ 添加商品行」时按首行结构克隆并清空，缓存为 `blank` 复用。`resetBlank()` 会先移除 option 上的 `selected` 属性再置 `selectedIndex = 0`，并同步重写 input 的 `value` 属性与当前值——否则 `cloneNode` 会按属性重建选中态，新增行会带着上一行的预选商品和单价。
- 删行不再兜底：任何一行都可删除（原先只剩一行时弹「一张单据至少需要保留一行商品明细」），删空后显示占位引导、合计归零并禁用提交按钮；采购 / 退货表单的提交条补上 `id="orderSubmitBar"`，与销售、自助下单共用同一套禁用逻辑。

### 3. 各页面的空态引导
- 采购 / 销售 / 无原单退货：占位提示指向「＋ 添加商品行」，该按钮同时恢复出现在新建采购单页头（v2.5 §4 的「去掉手工加行按钮」口径到此作废——空白行曾是唯一录入口，取消后必须补按钮）。
- 从原销售单「办理退货」进入：明细仍只能来自原单带入，不开放自由加行；若把带入的行全部删除，提示改为「🧾 退货明细已全部删除，请返回原销售单页重新点击「办理退货」」，提交按钮随之禁用。
- 客户自助下单：删行同步移出 `jc_cart` 购物车，删空后引导点击下方「＋ 继续添加商品」回商品目录重新选购。

### 4. 未做数据迁移
- 仅改渲染与前端交互，`parseItems()` 过滤空行的服务端逻辑、单据表结构与历史单据展示均未改动；旧单据的明细行照常显示。
